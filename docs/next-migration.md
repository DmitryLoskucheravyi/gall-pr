# Перехід на Next.js — план реалізації

Стан на 17.09.2026. Документ описує міграцію фронтенду з Vite + React Router
на Next.js (App Router). Бекенд (NestJS) не змінюється взагалі.

---

## 1. Навіщо і коли

**Що це дає, чого немає зараз:**

| | SPA + Pages Functions (зараз) | Next |
|---|---|---|
| `og:`/мета для ботів без JS | ✓ | ✓ |
| **Контент у сирому HTML** | ✗ | ✓ |
| JSON-LD, який бачать усі краулери | частково | ✓ |
| `canonical` + `hreflang` | ✓ | ✓ |
| Незалежність від черги рендеру Google | ✗ | ✓ |
| Core Web Vitals | без змін | помірно краще |

Вирішальний рядок — третій знизу. Google виконує JS, але другим проходом, у
черзі, з обмеженим бюджетом. На каталозі з сотнями робіт частина сторінок
просто не дочікується свого рендеру.

**Коли робити:** у вікно очікування верифікації еквайрингу (1–3 тижні
календарного часу, під час яких код нічим не заблокований). Міграція тоді не
відсуває запуск.

**Коли не робити:** якщо органічний пошук не планується як основний канал.
Тоді Pages Functions уже закривають превʼю в месенджерах, і цього достатньо.

**Оцінка:** 40–80 годин. Найдорожча частина — не сторінки, а авторизація.

## 2. Передумови

Виконати **до** початку:

- [ ] Перекодувати відео. Зараз головна тягне `hero-paint.mp4` 1.6 МБ +
      `corridor.mp4` 1.2 МБ з `preload="auto"`. Це вбиває LCP сильніше, ніж
      допоможе SSR, і Next цього не лікує.
- [ ] Підключити Search Console й аналітику, зняти базові показники. Без цього
      неможливо буде сказати, чи міграція щось дала.
- [ ] Закомітити все поточне. Міграція йде в окремій гілці — це єдиний виняток
      з правила «працюємо на main».

## 3. Рішення, які треба ухвалити першими

Від них залежить решта. Змінити їх на середині дорого.

### 3.1 Де рендериться кожна сторінка

| Сторінка | Стратегія | Чому |
|---|---|---|
| `/[locale]` (головна) | SSG + ISR | контент майже статичний, героїчні секції все одно клієнтські |
| `/[locale]/catalog` | SSR | фільтри й сортування в URL |
| `/[locale]/gallery` | SSG + ISR | |
| `/[locale]/painting/[id]` | **SSG + ISR** | ядро SEO; `generateStaticParams` по каталогу |
| `/[locale]/giveaways/[id]` | SSR | дедлайни змінюються |
| `/[locale]/support` (FAQ) | SSG + ISR | |
| кошик, замовлення, профіль, обране | клієнт | персональні, індексувати нічого |
| авторизація | клієнт | |
| `/[locale]/admin/*` | клієнт | |

ISR-інтервал: 3600 с для каталогу, ревалідація за тегом при зміні через адмінку
(якщо робити — див. 7.3).

### 3.2 Модель авторизації

Це найважче рішення в усій міграції. Зараз:

- refresh-токен — httpOnly cookie з `path=/auth`, `SameSite=Lax`
- access-токен живе **в памʼяті Redux**, ніде не персиститься
- `bootstrapAuth()` стукає на `/auth/refresh` **до першого рендеру**

Під SSR це не працює як є: сервер не має доступу до памʼяті браузера, а
`path=/auth` означає, що cookie не надсилається на інші маршрути.

**Варіант A (рекомендований).** Лишити авторизацію повністю клієнтською.
Сторінки, що її потребують, — клієнтські компоненти, як і зараз. Серверний
рендер працює лише для публічних сторінок, яким авторизація не потрібна.

- Плюси: нічого не переробляємо, ризик мінімальний, SEO-мета досягнута
- Мінуси: кабінет лишається з тим самим спалахом завантаження

**Варіант B.** Розширити cookie на `path=/`, читати її в Server Components,
робити `/auth/refresh` із сервера.

- Плюси: кабінет теж рендериться на сервері
- Мінуси: розширення `path` збільшує поверхню CSRF; треба перевірити кожен
  мутуючий маршрут; помітно більше роботи

**Беремо A.** Мета міграції — SEO публічних сторінок, а не швидший кабінет.

### 3.3 Хостинг

| Варіант | Плюси | Мінуси |
|---|---|---|
| **Cloudflare Pages + `@cloudflare/next-on-pages`** | лишаємось на Cloudflare, домен і DNS не чіпаємо | edge-рантайм, не всі Node API доступні |
| Vercel | найменше тертя з Next | ще один провайдер і рахунок |
| Node на тому ж дроплеті | все в одному місці | сам дроплет стає SPOF для фронту |

**Беремо Cloudflare Pages + next-on-pages**, бо домен, DNS і CSP уже там.

## 4. Фази

### Фаза 1 — каркас (6–10 год)

1. `npx create-next-app@latest web-next --ts --app --no-tailwind --src-dir`
2. Перенести `src/styles/` як є. SCSS-модулі в Next працюють без змін —
   `*.module.scss` підтримується з коробки, потрібен лише `sass`.
3. Перенести `_variables.scss` / `_mixins.scss`; глобальний імпорт через
   `sassOptions.additionalData` у `next.config.ts` — точний аналог теперішнього
   `css.preprocessorOptions.scss.additionalData` у `vite.config.ts`.
4. Каркас маршрутів:

```
src/app/
  layout.tsx                    → корінь, <html lang>
  [locale]/
    layout.tsx                  → Layout.tsx: Header/Footer/BottomNav/SupportWidget
    page.tsx                    → HomePage
    catalog/page.tsx
    gallery/page.tsx
    painting/[id]/page.tsx
    giveaways/[id]/page.tsx
    support/page.tsx
    support/chat/page.tsx
    (auth)/login/page.tsx       → group: без хрому, як CHROME_FREE_PATHS зараз
    (auth)/register/page.tsx
    (auth)/forgot-password/page.tsx
    (auth)/reset-password/page.tsx
    cart/page.tsx
    orders/page.tsx
    profile/page.tsx
    favorites/page.tsx
    admin/…/page.tsx
    not-found.tsx               → NotFoundPage
  sitemap.ts                    → замінює functions/sitemap.xml.ts
  robots.ts                     → замінює public/robots.txt
```

5. `middleware.ts` — редірект `/` → `/ua`, валідація сегмента локалі. Замінює
   `LocaleLayout`, який зараз робить це рендером.

**Перевірка фази:** порожні сторінки відкриваються за всіма URL, локаль
перемикається, стилі підхоплюються.

### Фаза 2 — і18n (4–6 год)

`react-i18next` працює, але під SSR потребує налаштування. Два шляхи:

- **Лишити `react-i18next`**, ініціалізувати на клієнті, а серверним
  компонентам віддати простий словниковий геттер (`getDictionary(locale)`).
  Менше змін у 21 сторінці.
- Перейти на `next-intl`. Чистіше, але переписуються всі виклики `t()`.

**Беремо перший.** JSON-файли локалей не чіпаються взагалі.

### Фаза 3 — дані (6–10 год)

1. `QueryClientProvider` у клієнтському провайдері, обгортка навколо `children`
   в `[locale]/layout.tsx`.
2. Для SSG/SSR-сторінок: `prefetchQuery` на сервері + `<HydrationBoundary>`.
   Публічні дані (картина, каталог) підуть у HTML; усе інше — як зараз.
3. `api/client.ts` лишається для клієнтських викликів. Для серверних — тонкий
   `lib/api-server.ts` без axios-інтерцепторів (на сервері нікого авторизувати).

**Пастка:** `store` (Redux) імпортується в `api/client.ts`. На сервері його
імпортувати не можна — звідси окремий серверний клієнт, а не спільний.

### Фаза 4 — сторінки (16–30 год)

Порядок — за SEO-цінністю, щоб кожен крок уже давав результат:

1. `painting/[id]` — ядро. `generateMetadata` + `generateStaticParams` + JSON-LD
2. `catalog`, `gallery`
3. головна
4. `support` (FAQ)
5. `giveaways/[id]`
6. кошик, замовлення, профіль, обране — просто `'use client'` зверху
7. адмінка — так само, вся клієнтська

Більшість компонентів переїжджає без змін. Що треба правити точково:

| Що | На що |
|---|---|
| `LocalizedLink` | обгортка над `next/link` замість `react-router` |
| `useLocalizedNavigate` | `useRouter()` з `next/navigation` |
| `useLocation()` | `usePathname()` |
| `useSearchParams` з react-router | однойменний з `next/navigation` |
| `<img>` у картках | `next/image` (тільки тут дає виграш на LCP) |

### Фаза 5 — анімації (4–8 год)

`useHeroSequence`, `CorridorSection`, `useScrollContinue`, `useAlternatingVideo`,
`Painting3DViewer`, `InteriorCarousel` — усе `'use client'`.

Виграшу від SSR тут нуль, але є ризик: вони читають розміри вікна й
`matchMedia` під час монтування. Перевірити, що немає розбіжності
сервер/клієнт при гідратації — інакше React зітре й перемалює піддерево.

`useScrollContinue` покладається на `document.documentElement.scrollHeight` —
переконатися, що він міряє після гідратації, а не до неї.

### Фаза 6 — SEO (4–6 год)

Те, заради чого все робилося.

1. `generateMetadata` на кожній публічній сторінці — title, description,
   `openGraph`, `alternates.canonical`, `alternates.languages`
2. `app/sitemap.ts` — портується логіка з `web/functions/sitemap.xml.ts`
3. `app/robots.ts` — портується `web/public/robots.txt`
4. JSON-LD — лишається як `<script type="application/ld+json">` у серверному
   компоненті; тепер потрапляє в HTML без жодних хитрощів
5. **Видалити `web/functions/`** — стає мертвим кодом
6. `usePageMeta` — видалити, його роботу забирає `generateMetadata`

### Фаза 7 — деплой (4–8 год)

1. `@cloudflare/next-on-pages`, збірка `npx @cloudflare/next-on-pages`
2. У Pages: build command, output `.vercel/output/static`, `nodejs_compat`
3. Змінні: `NEXT_PUBLIC_API_URL`, `NEXT_PUBLIC_TELEGRAM_BOT_USERNAME`,
   `API_URL` (для серверних викликів)
4. **CSP у `public/_headers` доведеться переписати.** Next інлайнить свої
   скрипти, тож хеш теперішнього скрипта теми стане непотрібним, а замість
   нього знадобиться nonce. Це окрема півгодини, і її легко забути.
5. Перевірити на preview-деплої **до** перемикання домену

### Фаза 8 — перемикання (2–4 год)

1. Preview-URL прогнати через Rich Results Test і Facebook Sharing Debugger
2. Звірити список URL зі старим `sitemap.xml` — **жоден не має змінитися**
3. Перемкнути Pages-проєкт на новий репозиторій/гілку
4. У Search Console: надіслати новий sitemap, стежити за Coverage тиждень
5. Старий проєкт не видаляти 2 тижні — це і є план відкату

## 5. Що НЕ мігрує

- **Бекенд.** NestJS лишається як є. Жодного API-роуту в Next — API вже існує.
- **JSON-файли локалей.** Переносяться як є.
- **SCSS.** 10.6 тис. рядків їдуть без змін.
- **Redux.** Лишається для теми, тостів і авторизації.
- **TanStack Query.** Лишається, додаються межі гідратації.

## 6. Реєстр ризиків

| Ризик | Ймовірність | Наслідок | Що робити |
|---|---|---|---|
| Розбіжність гідратації в анімаціях | висока | мигання, зірваний скрол | `'use client'` + `useEffect` для всього, що читає розміри |
| CSP забули переписати | середня | сайт без стилів або з помилками в консолі | пункт у чеклісті фази 7 |
| `store` протік у серверний бандл | середня | збірка падає або дивні помилки | окремий `lib/api-server.ts` від початку |
| Edge-рантайм не має потрібного Node API | середня | частина сторінок не збирається | `export const runtime = 'nodejs'` точково |
| URL змінилися непомітно | низька | втрата позицій | звірка списків у фазі 8 |
| Міграція затягнулась і зʼїла вікно еквайрингу | **середня** | запуск відсунуто | таймбокс: 3 тижні, далі відкат на SPA |

Останній рядок — найважливіший. Поставте дату, до якої або злилися в main, або
відкотилися. Незавершена міграція гірша за обидва варіанти.

## 7. Необовʼязкове, вже після

### 7.1 Контент
Сторінки серій, текст про художницю, розділ про техніки. Це дасть SEO більше,
ніж уся міграція — стек це ~30% результату.

### 7.2 `next/image` для каталогу
Cloudinary вже оптимізує, тож виграш лише в `srcset` і CLS.

### 7.3 Ревалідація за тегом
Вебхук з NestJS на `/api/revalidate` при зміні картини — щоб не чекати ISR.
Потребує секрету і роуту в Next; варто лише якщо каталог оновлюється часто.
